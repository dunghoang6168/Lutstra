# Lutstra: instructions for coding agents

Lutstra is a local-first desktop music player for lossless and Hi-Res libraries: Angular 21 in an Electron shell on Windows. The longer human guide is [docs/APP_GUIDE.md](docs/APP_GUIDE.md). The design system is [DESIGN.md](DESIGN.md), and its rules are binding.

## Hard rules
- **Stay in the UI layer unless the task says otherwise.** Do not change playback behaviour, `PlayerService` logic, gateways, `electron/`, IPC or the database.
- **No new dependencies.**
- **Angular style:** standalone components, signals and `computed`, `@if`/`@for` (never `*ngIf`/`*ngFor` in new code). Use external `.html` and `.scss` files (see [docs/FRONTEND_STRUCTURE.md](docs/FRONTEND_STRUCTURE.md)).
- **Tokens only.** Colours, spacing, radii, type, shadows and motion come from `src/styles/_tokens.scss` and `_themes.scss`. Do not hard-code values. If a value is missing, ask before adding a token.
- **Names:** the product is **Lutstra** and technical names use `lutstra`. Preserve the renderer origin `app://lutsra`, localStorage keys `lutsra.*` and IndexedDB name `lutsra-waveform` for existing browser data. Legacy profile migration also retains the old profile and database names to locate source data.
- **Keep accessibility:** real buttons and links, accessible names, visible focus, and the keyboard pattern described below.
- **Line endings:** keep LF.
- **Files to leave alone:** do not commit `docs/AUDIO_ENGINE_PLAN.md` or `skills-lock.json` unless asked.

## Design rules (full text in DESIGN.md)
- **Three layouts, one palette.** `html[data-layout]` is `inset` (Gallery), `classic` (Console) or `liquid-glass` (Ambient). Layouts change topology, never colour. Components read layout tokens (`--surface-radius`, `--control-radius`, `--row-height`, `--cover-*`, `--type-*`, `--motion-*`) instead of branching on layout.
- **Android has its own phone shell.** On Android, `main.ts` boots `PhoneAppComponent` (`src/app/phone/`) with `phoneRoutes`, and `ThemeService` sets `data-layout='phone'`: Gallery's palette and voice plus touch tokens (`--touch-target`, `--phone-*`, `--sheet-radius`). It reuses the services and gateways; desktop pages and components are not part of it (it has its own Settings page, with a Material You "Wallpaper" accent from `AppShell.getDynamicColors()` through `ThemeService.setDynamicPalette()` and `core/theme/dynamic-accent.ts`). Android Back reaches the web as the `lutstraback` window event; the shell closes the top dialog (by sending it Escape), then the queue sheet, then Now Playing, then goes back a page, and at Home moves the app to the background (`AppShell.moveToBack`). The phone's default accent is blue. Gestures (queue drag and swipe to remove, mini player swipe to change track, Library swipe between tabs) use `SwipeDirective` and `haptic()` (`AppShell.haptic`, the WebView's `performHapticFeedback`); their pointer listeners run outside Angular so a finger move never runs change detection. A swipe up on Now Playing opens the queue, and the bottom sheets close on a drag down from anywhere (`SheetDragDirective`, touch events so a list at its top hands the drag to the sheet); see `docs/ANDROID_DEVELOPMENT.md`. Plan: `plan/plans/android-phone-shell.md`.
- **Accent is meaning, not decoration.** It marks Hi-Res, active state, progress and focus. Accent text uses `--text-accent`. `--accent-primary` is for fills, rings and borders only. Do not use accent gradients or glows for ornament.
- **Amber means absence.** `--status-warning` / `--status-warning-text` are only for missing or unavailable files and disconnected outputs.
- **Ink play.** The play/pause control is `--text-primary` fill with a `--text-inverse` icon. Never accent, never glow.
- **Measurements are mono.** Format, bit depth and rate, kbps, times, counts and the signal path use the mono face with tabular figures. Prose never does. Format with `formatTrackFormat`, `formatResolution` and `trackQuality` in `src/app/features/home/library-quality.ts`. Hi-Res means lossless at 24-bit or above 48 kHz.
- **Type floor is 13px** (`--font-size-xs`). Console labels use `--type-label-variant` (small caps), never `text-transform: uppercase`.
- **Overlays:** text over artwork stays white on `--scrim-soft`, `--scrim-strong` or `--scrim-heavy`. Destructive buttons use `--status-error-fill`, `--status-error-fill-hover` and `--color-on-error`.
- **Copy:** sentence case everywhere: buttons, headings, aria-labels and tooltips. Page names (Home, Songs, Albums, Now Playing…) and engine names (Native Shared, Chromium Shared) keep their capitals. One item is a **track** ("Songs" only names the page).
- **Tooltips:** use `appTip` (icon-only controls and explanations; keep the aria-label) or `appTipOverflow` (truncated text, shown only while it overflows) from `src/app/shared/directives/tip.directive.ts`, never `title`. The one exception is the Gallery rail resize handle, where a cursor-anchored native tip suits a full-height strip.
- **Overflowing single lines in the Ambient dock** ping-pong with `appMarquee` (`shared/directives/marquee.directive.ts`, first child `.marquee-text`) and fall back to an ellipsis under reduced motion.
- **Playing cover art** goes through `app-cover-art` (`shared/components/cover-art`), which waits for the next cover to decode and crossfades to it at `--cover-fade-dur` (the layout's `--motion-dur`, 0ms in Console). Do not bind the playing track's artwork to a bare `<img>`.
- **One playback-mode control:** the Ambient dock and Gallery's Now Playing use one button that cycles Off → Shuffle → Smart Shuffle → Repeat All → Repeat One (`PlayerService.playbackMode`, `playbackModeIcon`, `playbackModeLabel`, `cyclePlaybackMode()`): accent when on, a muted repeat glyph when off. The Console strip and the Gallery rail keep separate shuffle and repeat; their shuffle button cycles Off → Shuffle → Smart Shuffle (the compass star icon) like repeat. S cycles shuffle the same way and R cycles repeat. Both cycles go through `SmartShuffleService.cycleShuffle()` / `cyclePlaybackMode()`, which start suggestions when Smart Shuffle is reached with nothing queued. See Smart Shuffle below.
- **Search ranking** lives in `shared/utils/search-rank.ts` (`rankMatches`, `normalizeSearch`: case and Vietnamese accents, `đ` included, are optional); the desktop global search and the phone Search page both use it.
- **Responsive:** respond to the `.main-content` container (`@container main-content (...)`, `cqi`), not the viewport, so Console's tree and inspector are accounted for.

## Listening history
`ListeningHistoryService` (`core/history`, started from `app.config.ts`) records every listen in the background to the `play_events` table: played seconds without seeks, furthest position, seconds seeked over, how it started and why it ended, and the source (`queue`, `roulette` for an external source, or `smart-shuffle`). It feeds Smart Shuffle (below).
- **Recording.** The pure logic lives in `listen-tracker.ts`.
  - `PlayerService.lastTransition()` tells a user skip from an automatic advance: the public transport methods mark it, and automatic advances go through the private `advance()`.
  - A listen within `max(3, crossfade + 1)` seconds of the end counts as `ended`. Each Repeat One loop is its own listen. Listens under a second are dropped.
  - A listen cut short by closing the app is kept in `lutstra.history.openListen` and recorded as `app_closed` on the next start.
- **History page** (`/history`, after Folders in the sidebar and tabs).
  - It lists only the track and when it was played, grouped by day. It is a log, not statistics: never show played time, skip reasons or sources.
  - `shownInHistory` leaves out listens from an external source (`roulette`) and removed suggestions; they stay in the database for the analysis.
  - Settings > Playback has **Clear history** behind a confirmation.
- **Storage.** IPC is `history:record`, `history:list`, `history:events` (everything, for the analysis) and `history:clear`. Android keeps it in an app-private SQLite database with the same table (`AndroidListeningHistoryGateway` / `AndroidHistoryPlugin`); the browser keeps it in memory (`MockListeningHistoryGateway`).
- `node scripts/listening-report.mjs` reads the database read-only and writes skip rates by source and week, 30-day library coverage and 3-day repeats to `plan/reports/listening-report.md`.

## Smart Shuffle
Smart Shuffle is a step of the shuffle cycles (above), shown with the `smart-shuffle` icon, the compass star `src/assets/icons/compass_star.svg`, drawn as a CSS mask (the earlier four-point star read as the Gemini logo). It is hidden with shuffle while an external source plays (`modesLocked`).
- **A queue mode, not an external source.** `PlayerService.smartShuffle` is exclusive with shuffle. `originalQueue` keeps the user's own order, and turning it off drops unplayed suggestions and restores that order; suggestions already heard stay where they played. Repeat does not apply while it is on, and its button is hidden in place.
- **Arranging.** `SmartShuffleService` (`core/smart-shuffle`, started from `app.config.ts`) calls `player.replaceUpcoming()` after the current entry.
  - It reorders the user's tracks by taste when it is turned on or tracks are added. Entries placed by Play next or a drag are `pinned` and stay put.
  - It puts a suggestion (`QueueEntry.suggested`) after every `suggestionSpacing()` user tracks: 5 to start, 4–8 from how the last 20 suggestions fared. Suggestions go only into the next `SUGGESTION_WINDOW` (10) slots, and fill the tail so playback never ends.
  - The next entry stays fixed for gapless playback. A skip or a removed suggestion rebuilds the ones after it.
  - With nothing queued, turning it on plays suggestions from a cold start.
- **The analysis is pure and seeded.**
  - `listener-profile.ts` turns listens into likes and dislikes with a 60-day half-life, per track and per artist, region (`trackRegions()` in `core/library`), genre, decade and hour bucket. A track rests for a day after it plays, then recovers over six days. The cold start uses library shape, new files, playlists and cached popularity when the edition provides it (`POPULARITY_GATEWAY`).
  - `smart-shuffle.ts` takes a Thompson sample from Beta(prior + own listens), links each pick to the track before it (artist, region, genre, era), never plays one artist three times running, and skips duplicates of queued songs.
- **Autoplay** (Spotify's, separate from Smart Shuffle). The `autoplay` setting keeps the queue playing once it ends. It defaults on everywhere (`AndroidSettingsGateway`, database and mock defaults); the switch is in Settings › Playback on the desktop and in phone Settings. While Smart Shuffle and repeat are off, `SmartShuffleService.autoplay()` keeps `AUTOPLAY_BATCH` (5) suggestions waiting after the queue, as Spotify's does. As soon as the queue has none, it appends a preview linked on from the queue's last tracks (`planUpcoming` with an empty `upcoming`, `player.appendSuggestions()`). When the first of them starts, it picks the rest again from the tracks really played (`player.replaceUpcoming()`, keeping user tracks added after it; `autoplayRefreshedId` makes this happen once). Each later suggestion that starts appends picks until 5 are waiting again. Turning Repeat on or Smart Shuffle on drops the unplayed ones (`dropUpcomingSuggestions`); they come back when Repeat goes off. The queue icon shows no track count, since Autoplay would keep raising it. The queue (desktop drawer, phone sheet) shows Autoplay's whole run with **Refresh** below it: `SmartShuffleService.refreshAutoplay()` picks every waiting suggestion again, leaving out every track in the queue so none comes back; Smart Shuffle's run still collapses to three behind **Show more**. They are ordinary `suggested` entries outside `originalQueue`: Add to queue goes before them, Shuffle on/off keeps them last, and `setAutoplay(false)` drops the unplayed ones. Daily Mix and playlists therefore play exactly in their order, then carry on.
- **Queue drawer.** On the desktop, Smart Shuffle's suggestions show the small `smart-shuffle` icon before the artist, and Autoplay's run at the end sits under an "Autoplay" divider; the phone queue marks them once with a divider that reads "Suggested by Smart Shuffle", or "Autoplay" while Smart Shuffle is off (`player.suggestionLabel`). Ones after the next track read quieter, since they may change. Smart Shuffle's run of suggestions at the end collapses to three behind **Show more**; Autoplay's shows in full with **Refresh**. Removing a suggestion records a mild dislike (`removed`, 0 seconds). Opening the queue (desktop drawer, phone sheet) scrolls the current entry, playing or paused, to the middle; the drawer also makes it the active row.
- **Flex Mix** (today's mix; the UI says Flex Mix on desktop and phone, while code, the `/daily-mix` route and the `lutstra.dailyMix` key keep the Daily Mix name). `DailyMixService` makes 30 picks a day through `SmartShuffleService.picks()` (the cold-start plan, so a new listener gets one too), keeps them in `lutstra.dailyMix` with the local day, and makes a new mix on a new day or on **New mix**. It plays as an ordinary queue with Smart Shuffle turned off, so skips teach the profile but never change the list; removing a track records `removed`. Home shows it as a wide card (Gallery, Ambient: cover mosaic, Play/Pause and New mix, five rows of the mix or of Up next) or a one-line band above the table (Console: Play/Pause, Open, "Playing 7 of 30 · next: …"); on the phone it heads Home. `isMixQueue(queue, mix, shuffled)` treats the mix as playing while the queue's own entries hold the mix tracks in mix order (with Shuffle on, in any order, as at least half the queue); suggestions and tracks the user added do not count against it. `DailyMixService.live`, `position`, `upNext`, `playOrPause()` and `playRow()` drive both Homes, so Up next follows the queue; Autoplay's picks stay in the queue.
- **Persistence.** The on/off state is the `smartShuffle` setting. `PlaybackSession` version 2 adds the indices of `suggested` entries; version 1 sessions still load.

## Track lists and keyboard
Every track table follows the same pattern: `role="grid"` with roving tabindex (one row in the tab order), ↑/↓/Home/End/PageUp/PageDown through `nextRowIndex` in `src/app/shared/utils/row-navigation.ts`, Enter for the row's main action, and Space left to global play/pause. Selection follows focus (`aria-selected`), and row actions are tabbable only on the active row. Songs and the album, artist and playlist detail tables also multi-select through `shared/utils/row-selection.ts`: Ctrl+click or Ctrl+Space toggles, Shift+click or Shift+arrows select a range, Ctrl+arrows move focus only, Ctrl+A selects all visible rows, and Esc collapses to the focused row. At least one row stays selected. From two selected rows, `app-track-selection-bar` covers the header. Row actions live in one `app-track-actions-menu` (⋯: Play next, Add to queue, Add to playlist…); both it and the selection bar open `app-add-to-playlist-dialog`, which marks playlists that already hold the tracks and asks before adding duplicates. Playlist detail adds tracks through `app-add-tracks-panel`, a non-modal right column (Songs / Albums / Artists / Folders, last tab saved as the `addTracksTab` setting) whose rows drag into the table with the `application/x-lutstra-tracks` payload. Detail pages read `route.paramMap`, not the snapshot, so a reused component reloads when the id changes.

## Editions
Lutstra builds in two editions. The **public** edition is this repository. The **full** edition adds the developer edition from `dev/`, a private repository of its own that this one ignores (`.gitignore`); `dev/README.md` documents it.
- **Seams.** Public code reaches the developer edition only through `src/app/dev-hooks/index.ts` (renderer: routes, providers, the header's Developer menu, Settings › About parts, a slot in the shell's content sheet and a Folders extension; types in `dev-hooks.types.ts`), `electron/dev-hooks.ts` (main process: window preferences, services, IPC through `DevContext.handle`) and `electron/dev-hooks-preload.ts` (preload APIs). These public files are stubs that add nothing; the full build swaps in `dev/renderer/index.ts`, `dev/electron/index.ts` and `dev/electron/preload.ts`.
- **Generic hooks behind the seams:** `ContentSheetService.embedded` (a page that embeds a site: the header folds the library search into its icon, Lutstra's player shows only while it plays, Console drops its inspector), `NavigationHistoryService.setInnerHistory` (Back and Forward walk a page's own history first), `ExternalSource.label` (the queue drawer's "<label> is playing"), and Folders' `FolderView` (`override` replaces the file list; the extension's column is `.col-extra`).
- **Builds.** `scripts/edition.mjs` picks the edition: `LUTSTRA_EDITION=full|public`, otherwise full when `dev/` exists, so a public clone builds as is. `npm start`, `npm run build`, `npm run electron` and `npm run package:win` follow it (angular.json's `full` configuration; `tsup.config.ts` swaps the Electron stubs). `npm run electron:public` and `npm run package:win:public` force the public edition, whose installer goes to `release/public`.
- **Keep developer features out of public files**: no developer code, names or behaviour here. Add a generic seam instead and put the feature in `dev/`. Before a public release, build `package:win:public` and check the bundles hold no developer strings.

## Verify before you report
1. `npx ng build` and `npx vitest run` (all files under `tests/`). `*.spec.ts` is gitignored, so commit new test files with `git add -f`, or name them `*.spec.mts`.
2. `node scripts/check-accent-contrast.mjs` when you touch colour tokens.
3. Look at the real UI. With a dev server running, `env -u ELECTRON_RUN_AS_NODE npx electron scripts/ui-sweep.cjs` covers every route × 3 layouts × 2 themes × 1440/560 and must report 0 flagged pages. It does not measure text over images, so check those screenshots by eye.
4. In your own probes, inject a no-transition style before measuring. Hidden windows freeze CSS transitions and give false results.
5. Stop any dev server you started.
6. Android changes (`android/`, `src/app/core/android/`): `npm run build:android`, then `android\gradlew.bat assembleDebug`, install on the Motorola (the only test device) and check there. `docs/ANDROID_DEVELOPMENT.md` has the status and how checks are driven over DevTools.

## Working alongside other agents
- Several agents may work at once. Work only in the folder and branch you were given (a git worktree for parallel work) and on the port you were given. Touch only the files the task names.
- **Do not commit, push, checkout, stash or reset** unless the task explicitly allows it. The reviewer merges.
- **Reply in Vietnamese (most important):** always talk to the user in Vietnamese, and write the files in `plan/` in Vietnamese too. Code, comments, commit messages and the English docs stay in English.
- **Working notes go in `plan/<type>/`:** every `.md` you create goes in the matching subfolder of `plan/` at the repo root (gitignored), never in a home or temp folder: `plans/` (plans, timelines), `prompts/` (prompts for other agents), `reports/` (task results, investigations), `reviews/` (code or design reviews), `notes/` (backlogs, drafts, anything else). This does not cover real project docs such as `docs/`.
- **Commit messages:** ask the user to approve the message before committing. Never add `Co-Authored-By`, a model name, or any AI attribution to commits or PR descriptions.
- Send a short plan first and wait for approval. In the final report, list changed files, test output, screenshots, any deviations from the task, and bugs you noticed outside scope. Copy before/after tables from `git diff`; do not reconstruct them.
